# amorphic-mlp

**Current work: the walking skeleton.** `docs/walking-skeleton-plan.md` holds the intention, the decisions and the slices. The framework is being built in `amorphic-systems/` beside the demo, and it must never depend on demo code. Before changing code, read the plan's "Decided" section and the brief for the current slice.

The source of truth for scope and stages is `docs/amorphic-mlp-plan.md`. Each of the plan's "repositories" is a top-level directory here. `amorphic-demo-env/README.md` has the demo walkthrough and real captured output. `docs/guide.md` is the step-by-step guide for newcomers, with output captured from a fresh clone; keep it in step with `./demo` when commands or output change. `./demo tour` (`scripts/tour.sh`) runs stages 0 to 4 with plain-words narration; keep its wording in step with the story.

- Java: one root Gradle build (`./gradlew build`), toolchain Java 21. Projects are `:pricing-calc-core`, `:pricing-calc-service`, `:amorphic-demo-app`, `:addressing`, `:envelope`, `:access`, `:inventory-core`, `:inventory-service`, `:governor-core`, `:governor-service`, `:topology` and `:composer`. The app pulls in core as a project dependency, not via mavenLocal.
- Fold-in: `-PfoldIn=true` puts core in the app's runtime classpath. Without it, core is `compileOnly`, and a `local` binding fails at startup (`Bindings`, `AddressTableFailureAnalyzer`).
- Python: `pricing-calc-py` uses uv (`uv run pytest`) on Python 3.12.
- Golden vectors live at `amorphic-demo-env/golden/vectors.json`. Java tests get the path from the `golden.vectors` system property (`GoldenVectors` in core's test fixtures); Python tests get it from the `golden_vectors_path` fixture. The golden set deliberately has no even-digit half-penny cases before v2.1.
- Monorepo tags carry a prefix: `pricing-calc-java/v2.0` (HALF_UP bug) and `pricing-calc-java/v2.1` (HALF_EVEN fix plus `RoundingRegressionTest` from the caught mismatch). `./demo` builds Java images from these tags (the core only; the service shell comes from HEAD, so commit before testing a shell change). Keep `PricingCalcCore.VERSION` and the Gradle `version` in step.
- Hot reload: `ReloadablePricingCalc` swaps routing when `POST /admin/address-table` applies a table. Each table is an evidence generation; late records from an older generation are dropped. Stage changes are live except folding core in or out, which rebuilds the app (agreed design). `./demo apply <file>` pushes a table by hand.
- Addressing: `:addressing` (`amorphic-systems/addressing`), plain Java with no dependencies, built to spec 01 (The Knowledge, `realising/specs/`). `Address` reads and prints the PURL form (canonical: qualifiers sorted), knows its rung (capability, range, version, implementation), narrows and broadens. `Version` is dotted numbers, the one scheme; `Range` is a wildcard (`2.*`, `*`). `Instance` names a manifestation (identity, realises, host). `Resolver` picks the highest matching version; floating requests skip withdrawn and planned versions, pinned ones resolve a withdrawn version with a warning, no match names both sides. Nothing compares addresses as text; wire shapes carry canonical text and parse at the edges. Framework tests use neutral examples (`greeter`), never pricing.
- Envelope and uniform access (spec 02): `:envelope` (`amorphic-systems/envelope`) is a header (`id`, `purpose` = the envelope's own spec, `pkg:envelope/request@1.0` or `reply@1.0`) plus named aspects, each with a `schema` address and a `body`; requests and replies need `payload` and `causation`; a failure is a reply under `pkg:schema/error@1.0`. `EnvelopeJson` is the wire form; built-in schemas ship in the jar (`Schemas`). `:access` (`amorphic-systems/access`) has `Invoker.invoke(address, envelope) -> Reply` (reply plus `Timing`) and three bindings: `LocalBinding` (a `Handler`), `RemoteBinding` (`POST {url}/invoke`) and `AdapterBinding` (maps the payload onto a plain GET and back; times the service). The catalogue says how each remote version is reached (`access: { via: envelope }` or an adapter) and lists schemas (`amorphic-demo-env/schemas/`); `Catalogue.schema` resolves them. In the app, `Bindings` builds an `Invoker` from the table binding plus the catalogue; `RoutingPricingCalc` sends one envelope per call (`PricingEnvelopes`) to champion and shadow; evidence lines carry `served_ms`/`served_service_ms` (and shadow). Java speaks the envelope natively (`InvokeController`); Python is unchanged, behind the adapter. `./demo` builds Java images from the core at the tag plus the service shell from HEAD (labelled, so they rebuild when either changes).
- Topology and the handshake (spec 03): `:topology` (`amorphic-systems/topology`) has `Topology` (caller plus roles, each with its step, role and the instance that answered; no generation), addressed `pkg:topology/<outcome>?hash=<sha-256>` (for example `pkg:topology/quote`), `CallRecord` (envelope id, `causedBy`, generation, topology) and `TopologyLog` (append-only JSON lines, read back on start). Instances are declared ahead in `amorphic-demo-env/instances.yaml` (`Instances`); the catalogue's `accept-undeclared` is false. Each pricing service answers `GET /meta` (identity from `AMORPHIC_INSTANCE`, realises from its own code) and Java replies carry an `instance` aspect (`InstanceRef`, `pkg:schema/instance@1.0`). `Bindings.bind` shakes hands with every remote role when a table is applied (`Handshake`; a mismatch is an `AddressTableException`); `./demo` waits on `/meta` before applying. Evidence comparisons are keyed by the pair of instances compared (each names its latest topology), so a quote and a report on the same instances count together; `/topology?address=` and `/topology/calls?address=`. Records go to `.run/records/topology.jsonl`. App tests answer `/meta` from the declarations (`TestServices`).
- Composition (spec 04): `:composer` (`amorphic-systems/composer`) has `Recipe` (an outcome `pkg:outcome/<name>@<version>` and its steps: capability, schema, `with` expressions over `input`/`item`/earlier steps, optional `each` fan-out with `pass-through`), `Router` (one `Routing` snapshot per plan; a `Route` is a served `Leg` plus an optional compared one), `Composer.run(outcome, envelope) -> Run` (every step an `invoke`, each caused by the outcome request; `completed` finishes after the comparisons with the shadow result and one recorded topology for the plan). Recipes live in the catalogue's `outcomes`. In the app, `Outcomes` asks for `pkg:outcome/quote` (`/quote`) and `pkg:outcome/account-value` (`/accounts/{account}/value`, `./demo report`); `ReloadableRouting` is the router (pricing-calc from the table via `PricingRoutes`, the canary chosen once per plan; positions and sum always local, `LocalCapabilities`, positions read `amorphic-demo-env/accounts.yaml`). Evidence gains `outcomes` (served result against shadow result). No controller names pricing.
- Inventory: `:inventory-core` (`amorphic-systems/inventory-core`), plain Java. `Inventory.observe(timeout)` returns `Observed`/`Unavailable`; `ObservedInventory` reads table, `/health` (`HttpHealthProbe`), evidence and `amorphic-demo-env/catalogue.yaml` on every call, storing nothing. The catalogue lists capabilities and tooling (catalogue, inventory, governor); `Tooling` holds the tooling addresses and default placements. Observation is by `/health`, never the Docker socket (agreed design). The app sets JVM DNS caching to 5s/1s so restarted containers are seen quickly.
- Governor: `:governor-core` (`amorphic-systems/governor-core`), plain Java. `RuleGovernor` applies `amorphic-demo-env/governor-rules.yaml` (first match wins) to the inventory, only when it is ready, and proposes a table rendered in the exact stage-file layout (`Tables.render`; tests assert each proposal equals the next stage file). A human approves (`/governor/proposals/{id}/approve`, `./demo approve`); approval is refused if the table generation changed, and fold-in returns `NeedsRebuild`. `Tables.guardHumanOnly` stops it changing the governor/inventory entries. Stage 1 stays manual (2.0 withdrawn). `GovernorHttp` defines the HTTP shapes the app, the service and `RemoteGovernor` share.
- Tooling bindings: the address table's `inventory`/`governor` entries (champion only, `local` or `remote`; no entry means local) route the app's `/inventory` and `/governor/...` per call (`RoutedInventory`, `RoutedGovernor`; `AddressTable.checkTooling`). Remote means `:inventory-service` (reads the app over `HttpSources`) or `:governor-service` (reads the app's `/inventory`, applies via `HttpTableSink`). Stage files hold only pricing-calc; `./demo` keeps tooling entries in `.run/tooling.yaml` and appends them to every table. Only a human moves tooling (`./demo tooling local|remote [inventory|governor]`).
- Stages are 0, 1, 1b, 2, 3, 3b and 4, with one `amorphic-demo-env/addresses/stage-<id>.yaml` each. The stage table in the plan is canonical. Run them with `amorphic-demo-env/demo`.
- App code map (`amorphic-demo-app/src/main/java/dev/amorphic/demo`): `QuoteController` (`/quote`, `/evidence`) and `AccountController` (`/accounts/{account}/value`) ask `compose/Outcomes`; `pricing/ReloadableRouting` (the composer's router, live table swaps), `pricing/PricingRoutes` (champion/shadow/canary), `pricing/Bindings` (remote/local), `compose/LocalCapabilities` (positions, sum), `evidence/EvidenceRecorder` (JSON log lines on the `evidence` logger plus counters).
